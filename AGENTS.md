# Gatefold agent notes

## Delivery

- Trunk-based. Each proven change ships as its own small pull request from `main`, opened after review and validation with auto-merge on, and merges on green ([prs-merge-within-30-minutes](https://github.com/ourostack/.github/blob/main/agents/prs-merge-within-30-minutes.md)). There is no merge order: a pull request waits on another only when it can't build without it.
- Merge as fast as possible; 30 minutes past green is the outer alarm, not the goal. Rebase it, fix it and merge it, or close it with a one-line reason and an issue for whatever is still worth doing.
- Don't stack fixes on a branch under review. A new finding during review is its own pull request, unless it's a defect in that pull request's own change.

## CI

- `app.yml` builds the app and its tests once (`Build for testing`, named by commit and Xcode version). Every simulator job downloads that build and runs `test-without-building`, and boots its simulator with `scripts/ci-simulator.py` while it downloads. Don't add `xcodebuild test` from source to a simulator job.
- UI tests run in shards of about 5 min of tests each (`.github/workflows/ui-tests.yml`, called from `app.yml`), split by each test's median pass on main. Every simulator job starts with the run and boots its new simulator while `Build for testing` builds (`.github/actions/await-build`). A shard's limit is 30 min of setup (the simulator wait step's own limit), twice its tests' slowest passes and 12 for the logs (the formula is in `app.yml`); the test step gets the twice-slowest budget whenever setup ends within those 30 min (`.github/actions/time-left`, gatefold#198); a shard that hits its limit is a red to fix at its cause, never a limit to raise. When a pull-request shard grows past about 5 min, split it; a new test goes in a catch-all shard (one with `skip:`) unless it is long. A test that alone takes longer than about 6 min runs on main only. Split it into shorter tests to bring it back to pull requests. `scripts/ci-shards.py check --expect scripts/ci-shards.expect` (in `CI scripts, offline`, which the required `GatefoldCore tests` stands for) fails when a listed test does not exist, runs in two shards, or a skipped test runs in no other shard, and when the set of tests CI runs differs from `scripts/ci-shards.expect`; after adding or removing a test, write that file from `--list`.
- Two tiers. A push to `main` runs every UI list; it is never cancelled, and a red there is the Red `main` owner's to fix. A pull request runs the build, the unit tests, `GatefoldCore tests` and at most about 5 UI jobs, chosen by the paths it touches (the `changes` job in `app.yml`): `smoke` (any app change), `place-undo` (the reader's place code, `GatefoldCore`, the app shell or project files), `place-jumps` (the place code or project files) and `taps` (the reader's chrome, settings, curl or design). A shard joins a pull request through its `pr_when` group and runs its `pr_tests` list there; every other shard is `pr_tests: none`. A pull request that edits a UI test class also runs that class on the device `main` runs it on, and one that edits the CI runs every list. `scripts/ci-shards.py` fails a pull-request list that has no `pr_when`. Keep the pull-request tier small: a guard test earns a place there only when it catches a break `main` would otherwise find an hour later.
- **Red `main` has an owner.** The Gatefold agent (a6b161f63fcc3159d) owns a red `main` here: it fixes it, or reverts the change that turned it red, before its next app pull request, and files an issue for a random red before any rerun. If the agent that merged the change is still working, it does the fix and the Gatefold agent sees it through. A red `main` counts on the PR clock, like a pull request over its time.
- Every required check reports on every pull request. A check that doesn't apply skips with a job-level `if:`, which reports success. A sharded check (`iPad (...)`, `Duo (the reviewers' checks)`, `Build and unit-test the app`) is a gate job with `if: always()` that is green only when every shard passed, or when only Markdown changed. Never gate a required check with a workflow-level `paths` or `paths-ignore` (gatefold#42).
- A newer push to a pull request cancels its older run. Runs on `main` are never cancelled.
- **TestFlight publishes only a green main.** `.github/workflows/testflight.yml` starts when App or Real unfold finishes on a main push and publishes that commit only when every check in `.github/required-checks.txt` passed on it (`scripts/ci-green-gate.py`). A red or replaced commit never publishes; the next green one carries its changes. Each published build is tagged `testflight/build-N`. When a required check is added to the branch protection, add it to that file.
