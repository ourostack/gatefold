# Gatefold agent notes

## Delivery

- Trunk-based. Each proven change ships as its own small pull request from `main`, opened after review and validation with auto-merge on, and merges on green ([prs-merge-within-30-minutes](https://github.com/ourostack/.github/blob/main/agents/prs-merge-within-30-minutes.md)). There is no merge order: a pull request waits on another only when it can't build without it.
- Merge as fast as possible; 30 minutes past green is the outer alarm, not the goal. Rebase it, fix it and merge it, or close it with a one-line reason and an issue for whatever is still worth doing.
- Don't stack fixes on a branch under review. A new finding during review is its own pull request, unless it's a defect in that pull request's own change.

## Interfaces follow Ouro UI

**[Interfaces follow Ouro UI](https://github.com/ourostack/.github/blob/main/agents/interfaces-follow-ouro-ui.md).** Every screen a person uses is built from Ouro HX, every door an agent uses is declared once with `ouro-actions` and checked by the Ouro AX X-ray in CI, Ouro is taken from its release tags (never copied by hand) and kept within a day of them, and what Ouro lacks is fixed in Ouro first.

**The bar, for people and agents alike** ([design craft](https://ui.ouroboros.bot/docs/design-craft/#the-bar)): would the people who made the Mac and the iPhone ship it? Whenever you scope or design something a person or an agent meets (a screen, a menu, a setting, a command, an action, a tool, a line of output):

1. Start from the jobs people do, in their words. Read a reference product's items, a service's functions or an API's fields as evidence of jobs, never as the list to build.
2. Make the first cut restraint: for each thing, name the job it serves and ask what breaks if it goes; if nothing does, leave it out and say why. Give each job one way in, not one per item or function, and extend the one that exists before adding another.
3. Build what is left well, the basics people use daily among it, for the person and for agents, with a result that says what it did.
4. Write how fresh people or fresh agents doing a real job will prove it, and rerun them after each small change.
5. Before you show a scope or design, follow the [`the-bar` skill](.agents/skills/the-bar/SKILL.md): a fresh agent that didn't write it checks every item against these steps, and you fix what it finds.

## CI

- `app.yml` builds the app and its tests once (`Build for testing`, named by commit and Xcode version). Every simulator job downloads that build and runs `test-without-building`, and boots its simulator with `scripts/ci-simulator.py` while it downloads. Don't add `xcodebuild test` from source to a simulator job.
- UI tests run in shards of about 5 min of tests each (`.github/workflows/ui-tests.yml`, called from `app.yml`), split by each test's median pass on main. Every simulator job starts with the run and boots its new simulator while `Build for testing` builds (`.github/actions/await-build`). A shard's limit is 30 min of setup (the simulator wait step's own limit), twice its tests' slowest passes and 12 for the logs (the formula is in `app.yml`); the test step gets the twice-slowest budget whenever setup ends within those 30 min (`.github/actions/time-left`, gatefold#198); a shard that hits its limit is a red to fix at its cause, never a limit to raise. When a pull-request shard grows past about 5 min, split it; a new test goes in a catch-all shard (one with `skip:`) unless it is long. A test that alone takes longer than about 6 min runs on main only. Split it into shorter tests to bring it back to pull requests. `scripts/ci-shards.py check --expect scripts/ci-shards.expect` (in `CI scripts, offline`, which the required `GatefoldCore tests` stands for) fails when a listed test does not exist, runs in two shards, or a skipped test runs in no other shard, and when the set of tests CI runs differs from `scripts/ci-shards.expect`; after adding or removing a test, write that file from `--list`.
- **A pull request and a merge-queue entry compile the app.** `Build for testing` runs there too, to compile only (no upload), whenever a changed file is one the build reads: anything but top-level Markdown, `docs/`, `changelog.d/`, `distribution/`, `screenshots/`, `tools/`, `GatefoldListingShots/`, `scripts/` and workflows other than `app.yml` (`changes` output `compile`; an empty or unreadable diff compiles). The required `Build and unit-test the app` is red unless it passed. It is the only macOS job there: #577 merged UI tests that didn't compile, and no TestFlight build could go out until #579.
- **macOS checks run on `main` after the merge, never on a pull request or in the merge queue**, except for a pull request that edits what orchestrates them (`app.yml`, `ui-tests.yml`, `.github/actions/`, `.github/scripts/`, `scripts/ci-*`; `scripts/ci-orchestration.py`), which runs them on itself (`changes` output `native`), except that compile: the unit tests, the Release build, every UI shard and Real unfold's unfolds skip there, and each gate reports success by saying so, so a pull request is judged by the Linux checks (`GatefoldCore tests`, `CI scripts, offline`, `Ouro actions and X-ray`) and that compile. A red run on `main` is the red-main alarm. macOS proof gates the release: TestFlight publishes a commit only when every required check, the macOS ones included, passed on that commit on `main` (`scripts/ci-green-gate.py`, `.github/required-checks.txt`), and the central auto-revert in ourostack/.github reverts the PR behind a `main` red for an hour. The paragraph below describes what `main` runs; the "pull request" tier in it is no longer run on a pull request.
- Two tiers. A push to `main` runs every UI list in a run of its own, never cancelled or replaced by a later merge, so every main commit gets a verdict; each of its macOS jobs waits in a main lane of its own, so a lone run starts them all at once and overlapping runs line up job by job, holding one run's worth of Macs (gatefold#246). A red there is the Red `main` owner's to fix. A pull request runs the build, the unit tests, `GatefoldCore tests` and at most about 5 UI jobs, chosen by the paths it touches (the `changes` job in `app.yml`): `smoke` (any app change), `place-undo` (the reader's place code, `GatefoldCore`, the app shell or project files), `place-jumps` (the place code or project files) and `taps` (the reader's chrome, settings, curl or design). A shard joins a pull request through its `pr_when` group and runs its `pr_tests` list there; every other shard is `pr_tests: none`. A pull request that edits a UI test class also runs that class on the device `main` runs it on, and one that edits the CI runs every list. `scripts/ci-shards.py` fails a pull-request list that has no `pr_when`. Keep the pull-request tier small: a guard test earns a place there only when it catches a break `main` would otherwise find an hour later.
- **Red `main` has an owner.** The Gatefold agent (a6b161f63fcc3159d) owns a red `main` here: it fixes it, or reverts the change that turned it red, before its next app pull request, and files an issue for a random red before any rerun. If the agent that merged the change is still working, it does the fix and the Gatefold agent sees it through. A red `main` counts on the PR clock, like a pull request over its time. Every `main` commit is tested in a complete run that includes it, though not necessarily its own (gatefold#246): a red run's `Merges this run covers` job lists the merges since the last green `main`, and the owner bisects them with probes of the failing shard only, never a full run.
- Every required check reports on every pull request. A check that doesn't apply skips with a job-level `if:`, which reports success. A sharded check (`iPad (...)`, `Duo (the reviewers' checks)`, `Build and unit-test the app`) is a gate job with `if: always()` that is green only when every shard passed, or when only Markdown changed. Never gate a required check with a workflow-level `paths` or `paths-ignore` (gatefold#42).
- A newer push to a pull request cancels its older run. A run on `main` is never cancelled or replaced: each main commit has a group of its own (`main-<sha>`). TestFlight is its own workflow, outside those groups.
- **TestFlight publishes only a green main.** `.github/workflows/testflight.yml` starts when App or Real unfold finishes on a main push and publishes that commit only when every check in `.github/required-checks.txt` passed on it in main's own push runs (`scripts/ci-green-gate.py`; a pull request's run on the same commit doesn't count). A red or replaced commit never publishes; the next green one carries its changes. Each published build is recorded as `testflight/build-N`: a deployment in the `testflight-builds` environment at its commit, which every job reading builds turns into a local tag (`scripts/ci-testflight-builds.py`; `list` prints them). GitHub refuses a workflow's token a new tag at a commit whose workflow files differ, so the workflow never tags; tags up to build 67 and any added by hand still count and win. When a required check is added to the branch protection, add it to that file.
- **Never test the same tree twice.** A run that ran the full lists (or every unfold) and passed ends with a job named `Full suite passed on tree <tree>` (or `Real unfold passed on tree <tree>`). A push to `main` whose tree a merge-queue or pull-request run already passed that way runs nothing: each required check reports success by that proof and names the run, so TestFlight publishes minutes after the merge. A push no such run passed, another tree, a red newest run or an unreadable API runs everything, as before (`scripts/ci-proof.py`, tested in `CI scripts, offline`).
- **App Store screenshots render on release only.** `.github/workflows/screenshots.yml` runs after TestFlight publishes a build, and only when something a shot can show changed (`scripts/screenshots/capture.py fingerprint`), or on a pull request that edits the screenshot pipeline. The scenes and captions are in `screenshots/spec.json`; `GatefoldListingShots` (its own scheme, outside App's shards) drives the app; the host shoots once the screen holds still, twice, and fails unless both passes match; `scripts/screenshots/compose.swift` draws the frames. Public-domain books only (`-GatefoldFakeShelf`), captions true to the app and free of trademarks.
- **Review panel shots run on dispatch only.** `.github/workflows/panel.yml` runs `GatefoldUITests/PanelCaptureUITests` on the iPhone Duo and the iPad, in light and dark, and uploads each screen as `panel-shots-<device>` (`scripts/ci-panel-shots.py` names them from the result bundle). It proves nothing, so no push, pull request or main shard runs it; start it with `gh workflow run panel.yml --ref main`.

## Ouro Feel

- **A jank report is first a missing Feel check.** When a person reports jank (a flicker, a jump, a lost place, something covered or under the status bar), first write the Ouro Feel check that would have caught it and see it fail in CI; then fix the app so it passes. If no Feel check covers the report, add it to Ouro UI for Apple ([ourostack/ouro-ui-apple](https://github.com/ourostack/ouro-ui-apple), its `docs/ouro-feel/README.md`) with a fixture page that has the bug, then use it here.
- `GatefoldUITests/FeelReaderUITests.swift` runs Feel over the reader on the iPhone Duo: folded, open in portrait and open on its side, each in scroll and paged mode (shards `duo-feel-closed` and `duo-feel-open`; the open one moves the hinge through Device Hub, `hinge: true`). Each test checks that nothing moves with no input, nothing covers the text, everything lies inside the window, and stray input keeps the place. A red the app still has is a mark in `FeelReaderUITests.known` naming its issue (an expected failure, never a skip); a strict mark fails once the check passes, so the fix removes it. A new reading mode or posture gets its test here.
